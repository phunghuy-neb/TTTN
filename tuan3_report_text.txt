XÂY DỰNG BACKEND QUẢN LÝ TOUR, USERVÀ CẤU HÌNH UPLOAD HÌNH ẢNH
Tóm tắt kết quả
Kết quả chính: Backend đã xây dựng các API xác thực, quản lý Tour, quản lý User dành cho Admin và cơ chế tải ảnh tour bằng Multer. Dữ liệu được lưu bằng MongoDB/Mongoose; các API thay đổi dữ liệu được bảo vệ bởi JWT và phân quyền theo role.
Nội dung tuần 3 tập trung hoàn thiện tầng Backend cho hai đối tượng nghiệp vụ cốt lõi là Tour và User. Phần Tour hỗ trợ lấy danh sách có lọc, xem chi tiết theo ID hoặc slug, tạo mới, cập nhật, xóa mềm và upload hình ảnh. Phần User hỗ trợ Admin xem danh sách, xem chi tiết, cập nhật thông tin và khóa/mở khóa tài khoản. Báo cáo này mô tả đúng trạng thái mã nguồn hiện tại, đồng thời chỉ ra các giới hạn cần hoàn thiện.
1. Mục tiêu và phạm vi thực hiện
Mục tiêu của nhiệm vụ là tạo nền tảng dữ liệu và API cho hệ thống VietVoyage, để giao diện Client, giao diện Admin và AI Service có thể sử dụng chung một nguồn dữ liệu có kiểm soát. Thiết kế ưu tiên tính phân lớp, khả năng bảo trì, bảo mật truy cập và khả năng mở rộng sang Booking, thanh toán và đồng bộ vector trong các tuần tiếp theo.
Xây dựng schema Tour đầy đủ: thông tin cơ bản, lịch trình, đợt khởi hành, hình ảnh, đánh giá, trạng thái và thông tin đồng bộ vector.
Xây dựng API quản lý Tour với tìm kiếm, lọc, sắp xếp, phân trang và phân quyền giữa khách vãng lai với Admin.
Xây dựng schema User và API quản trị người dùng: danh sách, chi tiết, cập nhật vai trò, khóa/mở khóa tài khoản.
Cấu hình upload ảnh bằng Multer, giới hạn định dạng và kích thước, đồng thời phục vụ ảnh qua Express static.
Duy trì bảo mật bằng JWT, bcrypt và Role-Based Access Control (RBAC).
Phạm vi: Tuần 3 chưa triển khai Booking, thanh toán, gửi email, AI Service hoặc giao diện Admin. Frontend danh sách/chi tiết tour hiện vẫn dùng dữ liệu mock, vì vậy báo cáo không mô tả việc tích hợp Tour API lên giao diện là đã hoàn thành.
2. Công nghệ và kiến trúc Backend
Backend sử dụng kiến trúc phân lớp Route – Middleware – Controller – Model. Route định nghĩa endpoint; middleware đảm nhiệm xác thực, phân quyền và tải tệp; controller xử lý nghiệp vụ; model định nghĩa cấu trúc dữ liệu và ràng buộc trên MongoDB.

4.1. Chỉ mục và tự động sinh slug
Schema tạo index theo cặp region–basePrice để hỗ trợ lọc tour theo khu vực và mức giá; index status phục vụ truy vấn các tour đang mở bán; slug là unique index để truy cập chi tiết tour bằng URL thân thiện.
TourSchema.index({ region: 1, basePrice: 1 })TourSchema.index({ status: 1 })TourSchema.index({ slug: 1 }, { unique: true })
Pre-save hook chuẩn hóa tên tour: chuyển về chữ thường, loại dấu tiếng Việt, đổi “đ” thành “d”, loại ký tự đặc biệt và thay khoảng trắng bằng dấu gạch ngang. Ví dụ “Vịnh Hạ Long – Kỳ quan trên biển” trở thành “vinh-ha-long-ky-quan-tren-bien”.
5. Thiết kế đối tượng User

5.1. Băm và kiểm tra mật khẩu
Pre-save hook chỉ băm password khi trường này thực sự thay đổi, tránh băm lại chuỗi hash ở những lần cập nhật hồ sơ. bcrypt tạo salt với cost factor 10. Instance method matchPassword dùng bcrypt.compare để so sánh mật khẩu người dùng nhập với hash trong cơ sở dữ liệu.
UserSchema.pre('save', async function (next) {  if (!this.isModified('password')) return next()  const salt = await bcrypt.genSalt(10)  this.password = await bcrypt.hash(this.password, salt)  next()})
6. Xác thực JWT và phân quyền
Các endpoint tạo, sửa, xóa tour và toàn bộ endpoint quản trị User đều yêu cầu token JWT. Client gửi token theo header Authorization: Bearer <token>. Middleware protect xác minh chữ ký bằng JWT_SECRET, tìm User theo ID trong token và kiểm tra isActive. Sau đó authorize('admin') xác nhận role trước khi chuyển sang controller.
Đọc token từ header Authorization và từ chối request nếu không có token.
Giải mã token bằng JWT_SECRET và lấy decoded.id.
Truy vấn User từ MongoDB; từ chối nếu tài khoản không tồn tại.
Kiểm tra isActive; trả 403 nếu tài khoản đã bị khóa.
Gắn User vào req.user để controller và middleware phân quyền sử dụng.
authorize('admin') trả 403 nếu role không thuộc danh sách được phép.
Phân biệt mã lỗi: 401 được dùng khi chưa đăng nhập hoặc token không hợp lệ; 403 được dùng khi tài khoản bị khóa hoặc người dùng đã đăng nhập nhưng không có quyền Admin.
7. API CRUD Tour
Tour API gồm hai nhóm: endpoint public để duyệt/xem tour đã published và endpoint Admin để tạo, cập nhật, upload ảnh hoặc xóa mềm. Nếu request GET có Bearer token hợp lệ, middleware tùy chọn sẽ nạp req.user để Admin có thể xem draft và archived.

7.4. Cập nhật Tour
PUT /api/tours/:id tìm bản ghi hiện tại trước khi cập nhật. Nếu có tệp mới, URL ảnh mới được nối vào mảng images hiện có. Khi name thay đổi, controller tự tạo slug mới và đánh dấu vectorSync.isSynced = false để AI Service biết cần đồng bộ lại. findByIdAndUpdate sử dụng new: true và runValidators: true để trả bản ghi mới và vẫn áp dụng validation.
7.5. Xóa mềm Tour
DELETE không xóa document khỏi MongoDB mà chuyển status thành archived. Cách xóa mềm giữ lại lịch sử và cho phép đối chiếu với Booking trong tương lai. Do API public chỉ trả published, tour archived tự động biến mất khỏi danh sách khách hàng.

10. Xử lý lỗi và response
Các controller sử dụng try/catch và trả JSON có trường success. ValidationError của Mongoose được chuyển thành 400 với thông báo đầu tiên; lỗi trùng unique key khi tạo Tour được chuyển thành thông báo trùng slug. Các trường hợp không tìm thấy trả 404; lỗi xác thực trả 401/403; lỗi không dự kiến trả 500.

11. Kiểm thử đề xuất và minh chứng
Mã nguồn Backend đã vượt qua kiểm tra cú pháp JavaScript. Để báo cáo có bằng chứng thuyết phục, cần chạy MongoDB và Backend, sau đó kiểm thử bằng Postman hoặc Bruno. Không nên chỉ chèn ảnh code; nên ưu tiên ảnh request, response và dữ liệu thực tế trong MongoDB.

12. Hạn chế hiện tại và hướng hoàn thiện
Phần triển khai đáp ứng tốt phạm vi nền tảng tuần 3 nhưng vẫn còn một số điểm cần cải thiện trước khi dùng trong môi trường production.
User chưa có POST/DELETE dành cho Admin, vì vậy chưa phải CRUD đầy đủ theo nghĩa tuyệt đối.
Frontend Tour vẫn đọc dữ liệu mock; chưa có bằng chứng giao diện gọi Tour API thật.
Lỗi Multer chưa được xử lý bằng error middleware tập trung, nên response lỗi upload có thể chưa đồng nhất.
Thư mục uploads là đường dẫn tương đối theo working directory; nên chuyển sang đường dẫn tuyệt đối dựa trên file module.
Bộ lọc kiểm tra extension và MIME type nhưng chưa kiểm tra chữ ký nhị phân của tệp.
Chưa có cơ chế xóa ảnh không còn sử dụng hoặc xóa ảnh khi cập nhật Tour.
updateTour chỉ đánh dấu cần đồng bộ vector khi name thay đổi; description, itinerary hoặc policy thay đổi cũng nên đánh dấu lại.
Các trường JSON trong multipart được JSON.parse trực tiếp; dữ liệu JSON sai nên được bắt riêng và trả 400 thay vì 500.
Chưa có test tự động bằng Jest/Supertest và chưa có tài liệu OpenAPI/Swagger.
Hướng phát triển tiếp theo là bổ sung Booking, tính giá và kiểm soát số chỗ bằng cập nhật nguyên tử; hoàn thiện Admin Dashboard; kết nối frontend với API; thêm lưu trữ ảnh trên Cloudinary/S3; và xây dựng bộ test tích hợp cho các endpoint quan trọng.
13. Kết luận
Nhiệm vụ tuần 3 đã hình thành Backend có cấu trúc rõ ràng cho VietVoyage. Tour schema đủ dữ liệu để phục vụ giao diện, Booking và AI trong tương lai; User schema đảm bảo đăng nhập và phân quyền; Tour API hỗ trợ đầy đủ luồng đọc, tạo, sửa và xóa mềm; User API cung cấp các thao tác quản trị thiết yếu; upload ảnh được kiểm soát bằng Multer. Kết quả này là tiền đề trực tiếp cho tuần 4 gồm Booking, tính giá, thanh toán và giao diện quản trị.
PHỤ LỤC A. Ví dụ kiểm thử bằng cURL
Các lệnh dưới đây là mẫu. Thay ADMIN_JWT và ObjectId bằng dữ liệu của môi trường kiểm thử. Trên Windows PowerShell có thể dùng curl.exe để tránh alias của Invoke-WebRequest.

PHỤ LỤC B. Danh sách ảnh nên chèn
Tài liệu đã có hai sơ đồ kiến trúc tự tạo. Để tăng tính thuyết phục, nên chèn thêm sáu ảnh chụp thực tế dưới đây. Mỗi ảnh cần có chú thích “Hình N”, khoanh nhẹ vùng quan trọng và giữ cùng một tỷ lệ chiều rộng.
